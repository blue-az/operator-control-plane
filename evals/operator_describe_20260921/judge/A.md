Operator is a local recordkeeping and verification-control system for AI coding work. The [README](inputs/01_github_README.md) describes the sequence as “tasks → claims → evidence → verifications.” A task records intended work; a claim is “a typed, checkable assertion bound to a gate”; the gate is an artifact path, while `verify_cmd` records a command for a verifier to rerun. Evidence attachment copies local files into retained snapshots and records SHA-256 fingerprints, sizes, and modification times. Remote references without retained bytes remain uncheckable.

The CLI stores current records as YAML under `.operator/` and versions trust-relevant writes in `.operator/ledger.sqlite3`. SQLite events contain full snapshots, transactional version numbers, and per-record hash links; triggers block updates and deletes. `doctor` compares history with projections, checks evidence fingerprints and identity metadata, and reports inconsistencies without repairing them. This is local audit storage, not an external tamper-proof record: the README says both stores occupy “the same writable disk.”

Identity enforcement is a separate mechanism. In `enforced` mode, builders create claims and draft evidence; registered verifiers attach status under an OS UID different from the claim author's. Only that verification is labeled `uid_isolated`. Default `single_user` verification is advisory. Different model or harness names do not create different authority identities, and Operator does not provision the Unix users. The README also admits that an agent able to edit local policy can weaken its own gate.

Around this core sit session and usage accounting, generated briefs, handoff records, and a delegation wrapper retaining instructions, optional frozen-path hashes, logs, and exit codes. Pi carries implementation work; Operator keeps the ledger. Static HTML boards summarize it. The [manual](inputs/03_reflect_operator-control-plane.txt) additionally describes catalog-validated study phases, approval and quota pauses, and checkpoint replay bound to a saved plan fingerprint. Its optional authority architecture adds a separate broker, external store, evidence content-addressed storage, receipts, reconciliation, and root-managed administration. Availability of that integration is disputed within the material.

The [Operator Shell page](inputs/02_operator-shell.txt) describes another architecture: “OpenClaw — Operator Access Layer,” five HTTP endpoints invoking shell scripts, ShowcaseAgent routing across nine domains, and Phoenix deterministic backends. Those components cannot be inserted into Operator's ledger architecture merely because the page shares the word “operator.” The README explicitly says Operator “does not import, invoke, or require Bulkhead Tau.” Graphify likewise maps Operator from outside; it is not the ledger's storage engine.

What the material actually demonstrates is narrower than its status language. The README's visible worked example writes `printf 'ok\n' > tests/out/upload.log`, then attaches that file with `--status verified`. Its comment says “--verify-cmd is inert audit metadata and is not executed by operator.” This demonstrates the proposed command sequence and how an advisory status can be recorded, not a successful test run. The claim says “uploader retries 3x on 5xx,” while the displayed test only evaluates `n <= 3`; no upload or HTTP failure is tested. The separate assertion that the runnable example “is executed on every CI run” supplies a script location and describes tampering/self-verification checks, but supplies neither that script nor CI output here.

The [board](inputs/05_board_pi-operator-extension.txt) supplies a concrete status snapshot: “15 tasks,” “10 verified tasks,” and “11/32 claims verified.” Step 1 is visibly marked “verified” alongside “1/4 claims verified.” Thus task status does not mean every associated claim is verified. Counts, IDs, and next actions are observable; underlying verification runs are not. The dogfood task is “quarantined,” with the instruction “Do not restore trust ... until an independent uid-966 verifier reruns against a coherent tree.” That names a required future method, not evidence that the rerun occurred. The board also reports credential, PATH, and provider-selection failures in generated review delegations.

The [Grok paper](inputs/04_paper_grok-built-into-operator.txt) goes beyond merely labeling contributions verified: “verification here means cross-referencing the session transcript ... against git log.” It names commits, a session, reproduction commands, and a correction exchange. The quoted correction and Grok's response support the reported format-selection mistake. However, the transcripts, commits, and filesystem artifacts themselves are outside this packet. The paper therefore describes an attribution-checking method; it does not let this reader reproduce it or establish UID-isolated acceptance. Its “two independently verified git commits” concerns recorded contribution, not proof that the committed software is correct. “Every artifact here traces to one 97-turn session” also limits the result.

The [Graphify page](inputs/06_graphify-demo_operator.txt) reports “183 nodes,” “449 edges,” and “3.1× fewer tokens per query.” It supplies a method: “graphify extract operator --code-only → graphify cluster-only → graphify benchmark,” plus an example neighborhood for `load_yaml()`, corpus/query token estimates, and three question-specific reductions. This is displayed measurement output with a named production pipeline, although the extraction does not provide raw benchmark records or establish preserved answer quality. It is evidence about Graphify's representation of Operator, not Operator's verification effectiveness.

The Shell page similarly reports “rule-based routing (41/41, 100%) against forced LLM routing (39/41, 95.1%)” and says its script reads three benchmark CSVs. That describes how the summary was produced, but not enough experimental setup or raw rows to reproduce the comparison. Its repair account says “Before-state captured ... after-state captured,” without showing either capture. The README's local-model sweep gives a more explicit design—216 cells, deterministic postconditions—and reports monotonic improvement for three of four models, while acknowledging a harness confound. These remain reported experiments with methods, not independently checked results in this packet.

There is a direct documentation disagreement about authority integration. The README says “operator and existing .operator ledgers do not consult the external authority yet.” The manual says “If the repository is enrolled, ordinary commit requests are role-gated and the broker becomes the authority boundary.” Its own configuration section repeats the README's non-integration statement. This is therefore both a cross-page disagreement and an internal contradiction. The manual identifies a source pin, but the packet does not reconcile these accounts. There is also conflicting relationship language: the Grok paper calls it “Bulkhead τ's Operator system,” whereas the README calls it “a standalone, domain-neutral control plane.” Ownership phrasing does not establish a software dependency.

Several specific questions remain unsettled:

- Which authority path is available in the documented product version? A single release pin, matching command reference, and enrolled CLI-to-broker execution trace would settle the integration contradiction; live installation and recovery tests would settle operational claims the manual explicitly leaves unexercised.
- What earned each board task its verified status? The transition rule, associated claims, evidence bytes, verifier UID, and actual rerun logs would distinguish partial acceptance from comprehensive verification and advisory from isolated status.
- Which cataloged harnesses work through current delegation? Versioned launch and completion traces, including verifier credentials and provider resolution, would settle the gap between catalog entries and the board's failed review paths.
- Do the measured reductions or stricter workflows preserve useful outcomes? Graphify needs matched answer-quality checks; Operator needs cases comparing accepted claims with independently established correctness. Neither token reductions nor retained hashes answer that question.

The likeliest misreading is that Operator establishes whether completed work is true. The README invites it directly: “an agent said it finished. Is that true, and did a different identity check?” Its actual boundary is narrower: “A vacuous gate (`assert True`) or a hash of irrelevant bytes can still look structurally valid.” Operator records evidence and controls who signs; semantic adequacy remains reviewer judgment. A verified label is not a machine-established proof of the claim.
