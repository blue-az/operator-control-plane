# Operator: an outsider’s description

## 1. What it is

Operator is a repository-local record and checking system for work performed by coding agents. Its basic object chain is task → claim → evidence → verification, with sessions, usage, and handoffs around it. The README’s mechanical description is: “The `operator` CLI records tasks → claims → evidence → verifications as YAML projections under `.operator/`, preserves every trust-relevant write in an append-only SQLite event history, binds writes to the executing OS identity, blocks same-UID ‘trusted’ verification in enforced mode, and ships a `doctor` consistency checker that fails closed.” The owner’s manual calls it “a local-first control plane for AI coding work” whose “center of gravity is a repository-local ledger.”

The local ledger has YAML directories for tasks, claims, evidence, handoffs, and usage, plus `.operator/ledger.sqlite3`. YAML is the compatibility/read projection; SQLite is the versioned event history. A claim is a typed assertion tied to a task and optionally a gate path and verification command. The listed claim types include `file_exists`, `test_passes`, `numeric_measurement`, `real_data`, `model_output`, `deployment_state`, and `paper_or_report_claim`. Evidence can be a local file or an explicitly schemed external URI. Local files are copied and fingerprinted. Evidence types include run logs, manifests, database queries, test output, commits, screenshots, transcripts, paper sections, and external documents.

The trust distinction is the central machinery. In enforced mode, a builder creates claims and draft evidence; a verifier with a different OS UID attaches status-bearing evidence. The README says only that case is recorded as `uid_isolated`; same-UID or default `single_user` verification remains advisory. The CLI does not create those separate users or containers. `doctor` is read-only: it checks event hashes, YAML projections, evidence fingerprints, required files, gate/test references, verification metadata, and self-verification. It deliberately does not execute stored verification commands.

Around this core are session and accounting commands (`session-start`, `session-end`, usage import and summaries), handoffs, briefs, headless delegation, and static HTML orientation boards generated from the ledger. The board snapshot reports 15 tasks, 10 verified tasks, and 11/32 claims verified, but it is a view of one project ledger, not the whole product.

There is also an optional, separate P3 path. The README describes `operator-broker` as an external authority store with evidence content-addressed storage, receipts, and projection snapshots, and `operator-admin` as root-managed installation/policy lifecycle. But it explicitly labels the broker “not installed,” says it is isolated from the existing CLI, and says current `operator` ledgers do not consult it. The owner’s manual likewise separates ordinary local work from enrolled authority, administration, and read-only snapshots. Thus the parts fit as a local ledger first, with an unintegrated external authority path beside it—not as one already unified service.

## 2. Demonstrated, or asserted

The strongest demonstrated behavior is the local record workflow. The README points to a runnable example “executed on every CI run” and says it “writes a real module, runs a real `pytest`, then tries two things that should fail.” It names the observed checks: editing attached evidence makes `doctor` report a SHA-256 mismatch and exit non-zero; a builder verifying its own claim under enforced mode is refused before writing. This is evidence of the example’s behavior as described, and the page gives the script and commands needed to reproduce it. It is not evidence that every listed command or policy works in every deployment.

The graphify page supplies a separate, concrete run over the `operator` source: “Real output from running graphify on operator: tree-sitter AST, code-only, no API key.” It reports “183 nodes · 449 edges · 11 communities · 8 source files,” and distinguishes “EXTRACTED — explicit in source (96%)” from “INFERRED — resolved by graphify (4%).” It also reports a benchmark result: roughly 12,200 tokens for a naïve corpus read versus 3,901 for an average scoped query, or “3.1× fewer tokens per query.” This demonstrates that a graphify analysis produced those numbers. It does not demonstrate that Operator itself uses Graphify, stores a knowledge graph, or reduces an agent’s context in normal operation. The board is explicit on this point: “not Graphify, not a knowledge graph.”

The live board demonstrates that a static project view existed at its snapshot time and that it displayed task statuses, evidence counts, handoffs, stale actions, and issue/future-feature labels. It does not independently establish the truth of each underlying claim. Indeed, it displays quarantined and stale tasks alongside verified ones. “Verified” there is a ledger status, not a described experimental method.

Several important statements are assertions or source descriptions rather than demonstrated runtime evidence. The owner’s manual says it was generated from a static source-tree snapshot, and explicitly states: “Runtime compatibility with external harness binaries” was not shown; “Live host behaviour for enrolled authority” was not exercised; and backup/migration restoration was not answered. It also says the support paths are “solid on validation, approvals, quota pauses, and replay checkpoints,” but “does not prove a full support list for every external provider.” Those are bounded assertions about the source/manual, not live demonstrations supplied here.

The Grok paper is a case study, not a product test. It claims one 97-turn session produced two independently verified commits and an analytical artifact, while also documenting a real miss. Its own limit is decisive: “every artifact here traces to one 97-turn session” and it is “not a general claim about Grok’s reliability.” The reported verification method is cross-referencing session transcripts with git history and filesystem artifacts, not relying on git author metadata. That supports the case study’s specific records, not a general performance claim about Operator or any harness.

The OpenClaw/Phoenix page should not be counted as Operator evidence. It describes five HTTP endpoints, Phoenix backends, and seven use cases under the statement “OpenClaw Makes Phoenix Accessible.” Nothing in that page identifies those components as Operator’s. Treating its “41/41” or “78% accuracy” as Operator results would be a category error.

## 3. What cannot be told

First, the material cannot establish live compatibility with the named external harness CLIs or providers. The manual says catalog entries are facts about source, not proof that each provider “still behaves as this product expects.” A matrix of real runs for each profile, with environment and results, would settle this.

Second, it cannot establish production behavior of the broker/admin path: the manual says real-host provisioning, enablement, rollback, and enrolled-authority behavior were not exercised, while the README says the broker is not installed or integrated. A controlled host installation and end-to-end broker/CLI test would settle it.

Third, it cannot establish recoverability beyond the append-only design. The manual expressly leaves backup and migration restoration unanswered. A documented backup, restore, migration, and failure-recovery test would be needed.

Fourth, it cannot establish semantic truth. `doctor` checks structure, metadata, and fingerprints and “deliberately does not execute stored verification commands.” The README acknowledges that a vacuous gate or irrelevant hash can look valid and that whether evidence proves a claim remains reviewer judgment. Independent reruns and substantive review of the gate would settle an individual claim; no supplied material establishes a universal solution.

Finally, the material cannot show that the reported board totals or graphify benchmark generalize beyond their snapshots and run. Fresh ledger exports and repeated, independently captured benchmarks would settle that.

## 4. The likeliest misreading

A technically literate reader could conclude that “verified” means the underlying software result was independently rerun and proved. The wording invites this: the README calls evidence and “a different-identity sign-off” the core, and the board labels tasks “verified.” But the same README says `doctor` does not execute `--verify-cmd`, and explicitly says structural validity can coexist with a vacuous gate or irrelevant bytes. Therefore “verified” establishes a recorded, identity-gated status under the ledger’s rules; it does not, from this material alone, establish that the claimed behavior is semantically true.
