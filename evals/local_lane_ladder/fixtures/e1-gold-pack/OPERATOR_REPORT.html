What this run answers

Scope and method

On a single-RTX-3090 desktop host, for three plan-shaped (L2) local-lane fixtures, how do deterministic postcondition pass rates compare across gemma4:26b, gemma4:31b, and a fully GPU-resident qwen2.5-coder:14b, at three trials per cell?

Every cell is graded by a machine-checkable postcondition that inspects the resulting files — never the model’s own narration or a self-reported success. Each task runs against a disposable temp fixture, so no real repository is touched.

Fixtures and their deterministic checks

alias-addExact line present in bash/.bash_aliases

L2 means plan-shaped prompting: exact paths, anchored edits, one tool call per step, an explicit success criterion, and bounded scope. This run does not re-derive the L0→L2 complexity ladder; it holds specificity constant and varies only the model.

The finding

Why 7/9 is not a capability result

Reviewer’s attention

qwen2.5-coder:14b produced the correct edit in all three trials. It received credit in one. The two failures are tool-call emission format, not wrong answers.

Below are the retained traces for the passing and failing trials of the same cell. The green lines are the harness dispatching a tool; their absence is the defect. The highlighted payload is identical across both.

[Model requests tool call: patch_file]
Arguments: {
  "tool": "patch_file",
  "path": "config/settings.ini",
  "target_content": "debug = false",
  "replacement_content": "debug = true"
}

[Tool Output]
Successfully patched config/settings.ini.

--- Output ---
[Tool completed: patch_file]
Successfully patched config/settings.ini.
trials 1 & 2 failed · 9.5s / 2.2s 
(no tool-call marker)

--- Output ---
```json
{
  "tool": "patch_file",
  "path": "config/settings.ini",
  "target_content": "debug = false",
  "replacement_content": "debug = true"
}
```
```json
{ "tool": "grep_search",
  "pattern": "^debug = true$" }
```

(no tool output — nothing executed)

The tool, path, target_content and replacement_content are byte-identical between the passing and failing trials. The difference is that trial 3’s emission was parsed as a tool call and dispatched, while trials 1 and 2 emitted the same JSON as fenced prose, which the harness printed instead of executing. No edit occurred, so the postcondition correctly reported the pattern missing.

The failing trials also emit two fenced blocks in one response — the edit plus a self-verification grep_search — which is the shape that fails to parse. The passing trial emitted a single call. The behaviour is intermittent for this model on this fixture.

Grading is correct; the defect is upstream of it

The grader did exactly what it should: it read the artifact, found no change, and failed the cell. Nothing about the scoring needs revision. What the raw number cannot express is why the artifact was unchanged, and that distinction is the whole point of retaining traces.

This belongs to the same family as a known historical confound in this project, in which a large batch of negative results could not be distinguished from harness truncation because no output had been kept. Those were pre-existing; this is a new instance under the current harness, which is why it is filed as a catalogued harness failure rather than folded into a model ranking.

Honest restatement of the third row

Do not cite “qwen2.5-coder:14b scores 7/9 at L2” as a capability finding. The supportable statement is: its answers were correct 3/3, and its tool-call emission parsed 1/3.

Instrumentation note

Why this finding was visible at all

Until immediately before this run, the eval runner captured the model subprocess’s stdout and stderr and then discarded both after grading, persisting only pass/fail, a detail string, a return code and wall-clock time. Under that runner, this matrix would have produced a clean-looking “qwen2.5-coder:14b: 7/9” and no reviewer could have distinguished a wrong answer from an unparsed tool call.

Per-cell trace retention was added first, and gated before any scoring: traces are written for passes, graded failures and timeouts, the write fails closed so an untraced cell cannot be silently recorded, and the option is off by default so unaltered runs behave exactly as before. This is the first run scored under it, and it immediately caught a confound. That is the argument for the requirement, demonstrated rather than asserted.

Reproduction

For the verifying reviewer

Run from the repository root on the desktop host. The matrix is resumable — completed cells are skipped, so an interrupted sweep restarts with the same command. 

OPERATOR_MACHINE=desktop python3 evals/local_lane_ladder/runner.py \
  --models gemma4:26b gemma4:31b qwen2.5-coder:14b \
  --tasks alias-add config-value-change function-add \
  --levels L2 \
  --trials 3 \
  --output   .../e1-gold-pack/RESULTS.md \
  --state    .../e1-gold-pack/state.json \
  --trace-dir .../e1-gold-pack/traces

Open items

Recommended next actions

  1. Independent re-derive by a distinct identity. Required before any result here is registered as a claim. Everything needed is retained.
  2. Decide the harness’s position on fenced-JSON tool emissions. Either accept them, or reject them with a distinguishable error so a parse failure can never again look like a wrong answer. The silent-print behaviour is the actual defect; both alternatives are preferable.
  3. Re-run the affected cell class at higher n to measure the emission-format rate, if the 14b floor seat matters to a downstream decision. Outside the present scope.
