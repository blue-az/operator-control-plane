Bulkhead Tau is described as a local expert-system substrate for domain-specific analytical tools, with contracts above execution and an evidence database below it. The home page calls its runtime “a pattern-matcher over grounded tools.” It borrows tau-bench’s organization—domain, policy/SOPs, tools, tasks, database, variations—rather than shipping Sierra’s evaluation or making an LLM the production runtime. This account describes software that recognizes requests, selects bounded operations, and works against domain data; it does not establish that every advertised surface implements that architecture.

The “Charter” means Product Behavior Contract specifications, `.pbc.md` files defining behavior patterns and routing constraints. The “Engine Room” is the deterministic executor, with supervisor/implementer rotation and a named four-phase framework: “Glass Box → Human-in-the-Loop → Progressive Disclosure → Multi-Modal Output.” The pages name those phases without explaining their transition rules. The “Logbook” is an append-only deliberation and trust-state design: SQLite `trust.db` under `.groundtruth_proto/`, recording behavior assertions against PBC anchors with seven-day verification leases. Its described gt-kb relationship is conceptual lineage and a parallel implementation, not repository identity. These details come from the [home capture](inputs/01_bulkhead-tau_home.txt).

[ShowcaseAgent](inputs/02_showcase-agent.txt) adds a proposed common entry point: a tkinter browser, `router/domain_router.py`, uniform domain adapters, and `unified_agent.py`. Its “meta-domain” routes work instead of executing domain tasks itself. Routing uses “regex patterns for speed, LLM fallback for ambiguous queries.” Meta-tool mode exposes 14 domain choices; direct mode exposes individual tools. Thus some advertised request selection does involve a model, despite the home page’s deterministic-runtime framing. The boundary between advisory selection and authorized execution is not explained.

[TennisAgent](inputs/03_tennis-agent.txt) describes a plan-then-execute engine over six merged SQLite databases containing watch, racquet, and fitness data. Tools perform classification, session linkage, visualization, and video analysis; five “smart” tools select sources and analysis types from context. Separately, the [BT Inc. manual](inputs/06_bt-inc-platform.txt) describes synthetic research desks: medtech matches prompts to six read-only analytical tools, while maintenance scripts write records; semiconductor variations add comparisons, notes, persisted SOP runs, plots, and HTML packs. Refresh normalizes sources, pulls data, and rebuilds SQLite from snapshots, continuing after individual failures. OSAT consults persisted review scores before generating advisory hypotheses. Portfolio tiers export 33, 42, 53, and 60 tools over sanitized data. These desk descriptions do not establish a common deployed application.

The distinction between evidence and assertion matters throughout. The captures contain architectural descriptions, counts, diagrams, and reported reviews, but no executable implementation or raw run records. The BT Inc. manual provides a repository commit identifier and names inspected components: “The medtech analyst command path, the desk service that opens SQLite, the six analyst tools, and the separate maintenance import scripts.” That describes a review method and its scope. Its phrase “Verified live shape” is not itself a runtime demonstration. The manual also excludes “Live databases, snapshots, or runtime state outside the reviewed code.”

Some boundaries are directly documented. BT Inc. is explicitly “a synthetic multi-domain conglomerate” and “not … evidence that a real operating company or unified production cockpit exists.” Portfolio is explicitly “sanitized Safe Mode: no live holdings, account numbers, transactions, or balances.” These passages establish the published scope; they do not independently demonstrate sanitization. The [Reflect shelf](inputs/07_reflect-shelf.txt) describes repository-generated chapters and attention cards subsequently refined by hand. It reports a fixed “healthy-while-serving-mock” bug and a “backend schema-init silent-gap,” but supplies neither reproduction nor before/after output.

Showcase reports “Overall routing accuracy: 80.6% (83/103 queries correctly routed).” The fraction supports the displayed percentage arithmetically. It does not show the queries, expected labels, predictions, model configuration, or scoring procedure. “150+ validation queries” describes the benchmark platform, not an explanation of why this result uses 103. Its hypothesis that local models perform better with meta-tools lacks comparative direct-mode results here. Routing accuracy also does not measure completion of domain work.

The [Local Models page](inputs/05_local-models.txt) reports “Three of sixty-six costs 27.6%” for CPU layer spill, without measurement configuration or timings in this capture. “Fourteen measurement faults caught in a week” is a count without the underlying cases. For “Under clean REST capture it passes all six probes,” the page does describe the intervention: replacing subprocess capture that embedded terminal sequences and corrupted multiline JSON. It does not provide probe definitions, responses, or scores. That is a reported result with a partial method, not reproduced evidence. Likewise, the home page dates the first trust entries to tennis-agent “LOSO graduation,” but supplies neither the graduation procedure nor its results.

There are explicit inconsistencies. The home page says “Downstream execution gating is specified but not yet wired” and “no caller currently enforces” its exit code, yet later calls the logbook “actively gating execution.” The [Domains page](inputs/04_domains.txt) says “Each domain is a deterministic agentic cockpit, gated by its own charter and grounded in real data.” That universal gating claim conflicts with the home page’s unwired downstream gate; no distinction between separate enforcement mechanisms resolves it here.

The pages also disagree on inventory. Showcase’s flow says “TennisAgent (171 tools)”; TennisAgent advertises “189 tools.” Showcase lists WQ with “38” tools; Domains says “41 tools across 7 projects.” Version or variation differences might explain these discrepancies, but the captures do not reconcile them. Reflect’s “192 tools” refers to `tennis-sensor-toolkit`, so it cannot automatically be treated as another TennisAgent count.

The manual contradicts itself about corrupt score history. Its additions say “corrupt or not a list” now blocks; an OSAT diagram explanation still says “When the score log is missing or unreadable … later hypotheses remain open instead of being blocked.” The text identifies a post-scan fix and supplies a pytest command, but no test output. That explains a possible revision boundary, not which behavior a running instance exhibits. The described score writer “verifies that the file was written by reading it back”; this checks persistence, not reviewer identity.

Specific unresolved questions, and what would settle them, are:

- Which callers actually enforce charter and trust decisions? A traced execution with passing, failing, stale, and disputed assertions, including rejected calls, would settle the home/Domain gating conflict.
- Can LLM fallback dispatch work outside deterministic constraints? The router-to-executor contract and an ambiguous-query trace showing authorization checks would establish that boundary.
- Which common interface exists? Showcase claims a unified router; BT Inc. says its shared shell is unverified. These concern different scopes, so they are not inherently contradictory. An integration map and cross-domain execution trace would show whether they connect.
- What currently governs OSAT review authority? The manual says reviewer values are caller-supplied and outer authorization unreviewed. Entry-point authorization evidence and corrupt/empty-history tests tied to a revision would settle identity and gate behavior.
- Which tools and data underpin advertised capability? Versioned registries would reconcile counts; source timestamps and a failed-pull rebuild trace would establish what a completed refresh actually contains.

The likeliest misreading is that Bulkhead Tau already enforces evidence-derived authority end to end across its domains. “Each domain … gated by its own charter,” “actively gating execution,” and “14 production domains” invite that conclusion. The explicit unenforced exit code defeats it. Desk-local controls and stored verification states do not demonstrate that execution stops when permission or evidence fails.
